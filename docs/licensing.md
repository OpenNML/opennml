# Licenses

Short version in the README, section "License".

## Overview

| Part | License | File |
|---|---|---|
| Source code of all own crates, programs and tools | GPL-3.0-or-later | `LICENSE` |
| `crates/opennml-bink` (port from FFmpeg) | LGPL-2.1-or-later | `crates/opennml-bink/COPYING.LGPLv2.1` |
| Documentation `docs/`, artwork `assets/` (program icon) | CC BY-SA 4.0 | `LICENSE-CC-BY-SA-4.0` |

The license texts come from the SPDX license list (crate `spdx` 0.13.4, versions `GPL-3.0` and `CC-BY-SA-4.0`).
`Cargo.toml` has `license = "GPL-3.0-or-later"` under `[workspace.package]`; each crate takes it over with
`license.workspace = true`, only `opennml-bink` sets `LGPL-2.1-or-later` itself.

## Code: GPL-3.0-or-later

- **Modifications stay open.** Anyone who changes the reimplementation and passes it on must provide the source code.
  For the reimplementation of an old game on which many people should work, this is intended; similar projects
  (OpenMW, OpenRA) do the same.
- **It fits the video decoder.** `opennml-bink` is a port from FFmpeg under the LGPL-2.1-or-later and is statically
  linked into every exe. The LGPL allows passing its code on under the GPL; together this gives a program under the
  GPL-3.0-or-later without special rules for distributing the exe. With a permissive license (MIT/Apache-2.0) the
  exes would still have carried the obligations of the LGPL.
- **"or-later"** keeps the way open to later versions of the GPL.

Rejected: `MIT OR Apache-2.0` (usual in Rust, but closed reuse would be possible, and the exe carries LGPL
obligations anyway because of `opennml-bink`).

## Documentation and artwork: CC BY-SA 4.0

Software licenses fit texts and images poorly. CC BY-SA 4.0 requires attribution and the same license for
modifications, which corresponds to the GPL for the code. This applies to the program icon (`assets/icon/`, own
design) and everything in this style in the future. The PNGs and `opennml.ico` are generated from the SVG sources and
are under the same license.

Exception in the documentation: where a file quotes third-party material (for example FFmpeg in
`crates/opennml-bink/README.md`), the license of that material applies to the quotation.

## Name and original

- The project is called OpenNML; "No Man's Land" appears only descriptively (what the reimplementation is for),
  together with the note in the README: not an official product, names and trademarks belong to their owners, no
  affiliation with the rights holders.
- You need your own original installation to play; the repository contains no original data.
- The program shows its own identifier at the bottom right ("OpenNML v..."). As in the original, the window title of
  `opennml-game` is "No Man's Land".

### Check

`deny.toml` sets the allowed licenses; `opennml-bink` is the only crate with an exception for the LGPL. The check is

    cargo deny check licenses

(tool: `cargo install --locked cargo-deny`, checked with 0.20.2). Run it whenever a change touches `Cargo.toml` or
`Cargo.lock`. If a new license comes in, it is added to `deny.toml` only after checking its compatibility with the
GPL-3.0-or-later, and added to the table here.

### Distributing the programs

Anyone who distributes an exe provides the source code or offers it (GPL-3.0 section 6), together with the license
notices of the dependencies.

The release archive (ZIP, flat) holds the exe, its PDB and these files, all generated by
`cargo run -p opennml-release -- files` into `target/release-files/`:

| File | Content |
|---|---|
| `README.txt`, `LIESMICH.txt` | what the program is, requirements, start, SmartScreen, firewall, where files are stored, removal, legal note, source code (English and German, same content) |
| `LICENSE.txt` | GPL-3.0-or-later (copy of `LICENSE`) |
| `licenses/COPYING.LGPLv2.1.txt` | LGPL-2.1 for `opennml-bink` (copy of `crates/opennml-bink/COPYING.LGPLv2.1`, with one line on the origin) |
| `licenses/CC-BY-SA-4.0.txt` | CC BY-SA 4.0 for the documentation and the artwork (copy of `LICENSE-CC-BY-SA-4.0`) |
| `licenses/THIRD-PARTY.txt` | the third-party crates of `opennml-game` with version and license, each license text once with the crates it applies to, plus fixed sections for the Rust standard library and FFmpeg |

`THIRD-PARTY.txt` is generated with `cargo-about` 0.9.3
(`cargo install --locked cargo-about --version 0.9.3 --features cli`) from `tools/opennml-release/about.toml` and
`about.hbs` for the target `x86_64-pc-windows-msvc` with the feature `gui`, so it lists the 148 crates (at the last
check) that end up in the exe and none of the project's own crates. `about.toml` accepts the licenses of the `allow`
list in `deny.toml` plus `LGPL-2.1-or-later`; a crate under another license makes the generation fail. For crates
under the MPL-2.0 (`symphonia*`) the file names the source location `https://crates.io/crates/<name>/<version>`
(MPL-2.0 section 3.2).

The source code offer is the repository and the archive "Source code" that GitHub attaches to every release; both
`README.txt` and `LIESMICH.txt` name them (GPL-3.0 section 6).

### C runtime

The release exe is meant to be built with `msvc-crt-static = true`: the C runtime (`libcmt.lib`, `libvcruntime.lib`,
`libucrt.lib`) is linked into the exe, so no `vcruntime140.dll` has to be installed. The question is whether Microsoft's
license terms allow passing on this code inside a program under the GPL-3.0-or-later. Checked on 2026-11-18 against the
toolchain used here (Visual Studio Community 2026, MSVC 14.51, Windows SDK 10.0.26100.0).

**What the terms say.**

- The Windows SDK terms (`Windows Kits\10\Licenses\10.0.26100.0\sdk_license.rtf`, section "Distributable Code") allow
  to "copy and distribute the object code form of code listed in REDIST.TXT files". For `.lib` files they require:
  "distribute only the results of running such Distributable Code through a linker".
- The Windows SDK redist list (<https://learn.microsoft.com/en-us/legal/windows-sdk/redist>, updated 2024-10-21)
  names, under "Static LIB files", the `.lib` files in `Windows Kits\10\Lib\<version>\ucrt\x64`
  (`libucrt.lib`) as distributable "when built as part of your program". So `libucrt.lib` is explicitly covered.
- The Visual Studio redist list (<https://learn.microsoft.com/en-us/visualstudio/releases/2026/redistribution>,
  `ms.date` 2025-11-11, the "REDIST.TXT" of Visual Studio 2026) names for the Visual C++ runtime the merge modules and
  "any of the files within the following folder and its subfolders": `VC\redist`. It does not name the static
  libraries in `VC\Tools\MSVC\<version>\lib\x64` (`libcmt.lib`, `libvcruntime.lib`) and does not mention static
  linking. Microsoft's page "Redistribute Visual C++ Files"
  (<https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files>, 2026-04-13) does not either.
  Microsoft documents `/MT` (static CRT) as a supported build option; its page "Using Microsoft C Runtime with
  User-Mode Drivers and Desktop Apps"
  (<https://learn.microsoft.com/en-us/windows-hardware/drivers/develop/using-the-microsoft-c-runtime-with-user-mode-drivers-and-apps>,
  2021-01-08) says of the VC++ pieces: "To avoid a runtime redistribution requirement, those pieces are statically
  linked." That describes the technique, not a license statement.
- The text of the Visual Studio 2026 license terms itself is shown by the installer and was not available to read on
  this machine (only the Windows SDK terms, the German `Licenses\1031\Redist.txt` and the online lists above). That the
  Distributable Code clause of the Visual Studio terms has the same wording as the one of the Windows SDK terms is
  **unverified**; the Visual Studio side is known only from the lists and from a Microsoft Q&A thread
  (<https://learn.microsoft.com/en-us/answers/questions/6034305/>), which is a community answer and not a statement
  of Microsoft.

**(1) Is the statically linked runtime Distributable Code?**

- `libucrt.lib`: yes, by the SDK list, as the result of linking it into the program.
- `libcmt.lib`, `libvcruntime.lib`: not stated. The lists do not name them, the terms do not exclude them, and a
  Microsoft Q&A thread of 2022 (<https://learn.microsoft.com/en-us/answers/questions/949795/>) shows that Microsoft
  staff found no guidance on static linking of the CRT either. Under the strict reading ("only the files on the list")
  they are not covered. Under the usual reading, the object code of the toolchain's libraries ends up in every program
  built with it, and passing it on is what the toolchain is for. The text does not settle which reading applies.

**(2) The "Excluded License" restriction.** The SDK terms forbid to distribute the source code of Distributable Code
"so that any part of it becomes subject to an Excluded License"; an Excluded License is one that requires, as a
condition of use, modification or distribution, that "The code be disclosed or distributed in source code form" or
that others have the right to modify it. The GPL is such a license for the program as a whole.

- The restriction speaks of the *source code* of Distributable Code. The release build does not distribute CRT source
  and does not modify the CRT; the exe is meant to contain only the object code that the linker takes from the
  `.lib` files.
- GPL-3.0 section 1 excludes the "System Libraries" of an executable work from its Corresponding Source. Two
  conditions apply: the library is "included in the normal form of packaging a Major Component" (a Major Component
  includes "a compiler used to produce the work") without being part of it, and it "serves only to enable use of the
  work with that Major Component". The C runtime libraries come packaged with the MSVC toolchain, which is the first
  condition; that they serve only to enable use of the work with the toolchain is plausible (they provide the runtime
  the compiled code needs) but not established. If both hold, the GPL does not require to disclose the CRT source or
  to license it under the GPL, and the CRT stays under Microsoft's terms instead of "becoming subject to" the GPL.
- Open question: the GPL exception is written for the Corresponding Source. Whether it also takes the linked object
  code out of the license grant for the whole work (section 5 c) is not settled by the text, and the Microsoft terms
  do not say how they see it. No court decision or statement of Microsoft on this was found.

**Conclusion: UNCLEAR.** `libucrt.lib` is explicitly allowed. For `libcmt.lib` and `libvcruntime.lib` the terms
neither allow nor forbid it in so many words, and the interplay of the Excluded License clause with the GPL is not
settled. The readings above make it plausible that it is allowed, but this is not a legal opinion and nothing found
confirms it. Ways to settle it: ask Microsoft licensing (VS support) in writing, or read the Visual Studio terms of
the edition that builds the release on the CI runner.

**Position of the project.** OpenNML builds the release with the static runtime (`msvc-crt-static = true`). The open
point stays recorded here: there is no explicit statement for `libcmt.lib` and `libvcruntime.lib`. The fallback
remains as follows: `msvc-crt-static = false` (dynamic runtime) and a note in the readme to install the "Visual C++
Redistributable" from Microsoft; then the exe imports `vcruntime140.dll` and `ucrtbase.dll`, and the import check of
`opennml-release` has to allow them.
