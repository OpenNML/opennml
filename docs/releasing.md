# Releasing

A release is a ZIP archive for Windows x64 with the game `OpenNML.exe`, attached to a GitHub release together with
its SHA-256 checksum. It is built in GitHub Actions when a version tag is pushed; nothing of it is built or uploaded
by hand.

## Tools

| Tool | Version | Where |
|---|---|---|
| [`dist`](https://axodotdev.github.io/cargo-dist/) (formerly cargo-dist) | 0.34.0 | `cargo-dist-version` in `dist-workspace.toml`; CI installs this version |
| [`cargo-about`](https://github.com/EmbarkStudios/cargo-about) | 0.9.3 | CI installs it with `taiki-e/install-action` (`.github/build-setup.yml`) |
| `opennml-release` | workspace | `tools/opennml-release` |

Local installation (only needed for the local trial build below):

    cargo install --locked cargo-dist --version 0.34.0
    cargo install --locked cargo-about --version 0.9.3 --features cli

The binary of `dist` is called `dist` (there is no `cargo dist` subcommand). `cargo-about` installs its binary only
with `--features cli`.

## What `dist` does

The configuration is the `[dist]` table in `dist-workspace.toml`, plus `[package.metadata.dist]` in
`apps/opennml-game/Cargo.toml`, the only package with `dist = true`. `dist`:

- builds `opennml-game` with the feature `gui` (no console window, see [programs.md](programs.md)) in the cargo
  profile `dist` (`Cargo.toml`) for the one target `x86_64-pc-windows-msvc`, with the C runtime linked statically;
- packs the ZIP `opennml-game-x86_64-pc-windows-msvc.zip`, flat (without a root folder), with the exe and the files
  under `include`: the PDB of the exe and the readme and license files from `target/release-files/`
  (`auto-includes = false`, so it picks up nothing else);
- writes the checksum files (`.sha256` next to each artifact and `sha256.sum`);
- on a tag, creates the GitHub release and uploads the artifacts. There are no installers.

`.github/workflows/release.yml` is generated by `dist generate` from that configuration and is never edited by
hand. After a change to `dist-workspace.toml` or to the dist metadata, run `dist generate` and commit the result;
`dist generate --check` reports a workflow that is out of date. For a pull request the workflow only runs
`dist plan` (`pr-run-mode = "plan"`).

## The project's own steps

- `.github/build-setup.yml` (`github-build-setup`): steps `dist` inserts into the build job before the build. They
  install `cargo-about` and run `cargo run --locked -p opennml-release -- files`, which writes `README.txt`,
  `LIESMICH.txt`, `LICENSE.txt` and `licenses/` (LGPL and CC BY-SA texts, third-party overview from `cargo-about`)
  to `target/release-files/`. `dist` checks that the `include` paths exist only when it packs the archive.
- `.github/workflows/check-release.yml` (`global-artifacts-jobs`): a reusable workflow `release.yml` calls after the
  build. On `windows-latest` it fetches the built archive, unpacks it and runs
  `cargo run --locked -p opennml-release -- check <folder>`, and logs the size of the ZIP and of the exe. The `host`
  job, which creates the release, waits for it: if the check fails, there is no release.
- `opennml-release` (`tools/opennml-release`) reads the shipped package, its version and the exe and PDB names from
  `cargo metadata`:
  - `files [--out <folder>]` generates the readme and license files (default `target/release-files`);
  - `check <folder>` checks an unpacked archive: exactly the expected files, text files with CRLF and UTF-8 without
    BOM, the exe a 64-bit GUI program that imports only allowed system DLLs (no Visual C++ runtime). Every output line
    is one finding; the exit code is 0 only without findings;
  - `inspect <exe>` prints machine, subsystem and imports of an exe.

  The test `dist_config_matches_binary` fails if `dist-workspace.toml` and the binary drift apart (for example the
  PDB name in `include` after a rename of the binary).

## Release procedure

1. A release pull request sets `[workspace.package] version` in `Cargo.toml` to the new version `X.Y.Z` (and updates
   `Cargo.lock`). The workflow plans the release on the pull request; check its `plan` job.
2. Merge the pull request.
3. Create an annotated tag on the merge commit and push it:

       git tag -a vX.Y.Z -m "OpenNML vX.Y.Z" <merge commit>
       git push origin vX.Y.Z

   The tag must match the version in `Cargo.toml`; a suffix like `-rc.1` makes a prerelease.
4. The tag starts the `Release` workflow: plan, build, check, release.
5. Check the release: it has the ZIP and its `.sha256` file; download the ZIP, compare its checksum
   (`Get-FileHash <zip> -Algorithm SHA256`) with the `.sha256` file, unpack it and run
   `cargo run -p opennml-release -- check <folder>`; start `OpenNML.exe` once.

Tags are never moved or deleted. If a release is broken, fix it on `main` and release a new version.

## Local trial build

    cargo run -p opennml-release -- files
    dist build --artifacts=local --target x86_64-pc-windows-msvc

The archive is in `target/distrib/`. Unpack it and check it with `cargo run -p opennml-release -- check <folder>`.
A local build contains the local user name and paths in the exe and the PDB; only archives built in CI are shipped.

## Signing

The exe is not signed yet, so Windows SmartScreen may warn on the first start. Until it is signed, the SHA-256
checksums of the release are the way to check a download.
